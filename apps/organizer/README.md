# Unfiled encrypted organizer

`@unfiled/organizer` is the separately deployable AI-assisted create-or-append trust domain. It is not the web application, index worker, or verifier. It accepts no browser session, owner identifier, Supabase API key, broad database credential, static AWS credential, private-manual key, or ambient provider credential. Production requires one server-only `UNFILED_ORGANIZER_OPENAI_API_KEY` scoped to a dedicated OpenAI project/service account for app-default routing and explicitly enabled fallback. A user OpenAI key can enter this process only transiently through the live-lease Vault resolver; it never enters HTTP input, environment configuration, logs, caches, jobs, envelopes, or durable process state.

## Security boundary

- Production PostgreSQL identity is exactly `unfiled_organizer_worker`. TLS uses hostname verification and a pinned CA chain. The executor permits only identity preflight and eleven reviewed RPCs: claim, heartbeat/revalidate, bounded candidate projection, bounded encrypted-RAG pagination, exact ranked-candidate selection, prepare create, prepare append, atomic commit, fail, recovery, and lease-bound provider credential resolution.
- Claim and candidate RPCs supply only lease-bound, byte-bounded AI-assisted ciphertext and the exact wrapped key records required to open it. The app never accepts an owner ID from the request.
- Each candidate page carries the database-current consent controls and authoritative `isOpen` state. The organizer binds the exact controls plus `{candidateId,noteId,revision,isOpen}` manifest into revalidation, and it never decrypts a closed candidate for the planner.
- The organizer renews the authoritative lease immediately before a planner could receive plaintext and again immediately before atomic commit. A privacy flip, deletion, consent edit, lease loss, or stale revision that wins before either point fails closed.
- Every provider attempt resolves the immutable job's OpenAI source under the current job ID and live lease token. App-default returns no database secret and uses the dedicated environment key. BYOK returns one Vault-decrypted credential plus its revision, held in an erasable byte buffer and decoded only at the outbound request boundary. Retries resolve again; a lease never receives a different revision, while a fresh attempt may use a replacement key. A 401/403 is bound to the exact disclosed source/revision before the database can invalidate it or activate an explicitly snapshotted fallback.
- When active-generation RAG coverage is complete, the organizer sends the capture text alone to the OpenAI Embeddings endpoint using the generation-pinned model and dimensions. It decrypts and exact-scans that owner's bounded encrypted index pages in memory, then asks the database to project only the exact top-ranked, current-revision candidates. Missing, stale, malformed, or incomplete retrieval disables RAG-derived auto-apply and falls back to the narrower lease-bound candidate path.
- The OpenAI planner sends a foreground Responses request with strict Structured Outputs, `store: false`, no tools, no conversation state, and no background response. It discloses the capture plus at most eight open candidates, each reduced to an ephemeral candidate ID, bounded title/type, at most three bounded headings, and a bounded latest snippet; candidate bodies, capture/job/owner IDs, and database note IDs are not sent.
- The routing profile is code-pinned to prompt/schema `routing-v1`/`1`, model snapshot `gpt-5.4-mini-2026-03-17`, a 20-second absolute provider deadline, bounded request/response/output sizes, and one retry only for transport, 408, 409, 429, or 5xx failures. The immutable economical/standard/thorough setting changes only candidate and provider reasoning/output budgets; it never changes safety bands. Expansion off is enforced by the database-current controls and plan authorization; brief drops generated text above 200 characters, while detailed retains the existing 600-character contract ceiling. Caller cancellation wins and is checked again before any publication.
- `store: false` disables Responses application-state storage; it does not apply to the separate Embeddings request and is not by itself a Zero Data Retention guarantee. OpenAI documents no application-state retention for `/v1/embeddings`, but default abuse-monitoring logs for API traffic may contain customer content and may be retained for up to 30 days unless the deployment's project is approved and configured for Modified Abuse Monitoring or Zero Data Retention. API data is not used to train OpenAI models by default unless the account opts in. See the official [Responses reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) and [API data controls](https://developers.openai.com/api/docs/guides/your-data).
- `@unfiled/ai-routing` is the sole unknown-plan parser and authorization/materialization boundary. The app first authorizes the candidate manifest, then obtains database-issued stable IDs and reservations, then materializes. Model-selected IDs are never persisted.
- An explicit destination must remain owned, eligible, open, and present in the authorized manifest. Expansion-disabled input cannot produce expansion. E3 reserves and seals an authorized expansion as a separate encrypted `proposed` generated block plus encrypted pending-expansion Review in the same atomic commit as the routed result; generated bytes never enter the user-authored note snapshot. Duplicate suspicion produces only an encrypted Review with bounded revisioned candidates and no note-mutation authority.
- A stale append may re-plan once. The first conflict atomically burns the old reservation and rebinds preparation; a second conflict returns `review_required` without publishing the stale command. The service discards the conflicted page, fetches and revalidates a current page, then seals and atomically commits a real Review command, so the database never reinterprets append ciphertext as Review.
- Reservation IDs bind the stable job identity, durable claim attempt, and deterministic per-write generation. Every database conflict that burns or invalidates a preparation advances the write generation; same-generation replay is idempotent while replan, refreshed Review, retry, and recovery cannot reuse a consumed reservation.
- The KMS workload is `organization_worker`, limited to AI-assisted object-wrap and content-MAC roots. Private-manual content cannot be projected or decrypted.
- Logs contain only a server-generated request ID, route, method, runtime, status, duration, retryability, and a safe error class. Caller-provided request IDs are ignored; the generated ID is shared by the response, log, and drain invocation for safe correlation. Responses and logs never include note or capture content.
- Claimed/candidate state is released synchronously from warm-process memory in a `finally` path, including when request abort prevents the failure RPC from running.

## Current milestone boundary

C.5c-3 supplied the isolated runtime, database adapter, lease-linearized drain, canonical plan authorization/materialization, stable idempotency bindings, KMS authority, cancellation, and atomic commit port. Milestone D adds the production content-mutation cipher, encrypted RAG retrieval and selection, strict OpenAI Responses planner, embedding adapter, deterministic extraction/source-preservation checks, conservative scoring, create-or-append application, and encrypted Review publication. E3 extends the existing prepare/commit payloads with independent generated-block identity, wrap reservation, encrypted content, immutable model/prompt provenance, Review binding, and non-destructive duplicate metadata. E4 adds the sole eleventh organizer capability: Vault-only, live-lease OpenAI source resolution with exact-revision failure binding. Deterministic planners, transports, and ciphers remain injectable in tests, but there is no deterministic deployed fallback.

`pnpm eval:routing` runs 175 checked-in cases against a deterministic mock plan generator and the real parser, extraction, preservation, authorization, and policy code. `pnpm eval:routing:pipeline` separately exercises a production-component seam through real retrieval/ranking, authorization, preservation, materialization, policy, and application code with deterministic provider output. Its report sets `liveProviderEvidence=false` and explicitly excludes database lease/heartbeat, encrypted seal/persist, and repository select/commit generation revalidation. The optional `pnpm eval:routing:live` command requires `UNFILED_ROUTING_EVAL_OPENAI_API_KEY`, invokes the same strict OpenAI planner over eligible frozen synthetic pipeline cases exactly three times each, and emits only content-free version/hash, status, latency, token, cost, decision, and worst-of telemetry. No credentialed live run or report exists yet. Before enabling real personal-note traffic, record that dated report and complete the Production canary and rollback gate in `HUMAN_SETUP.md`.

Stored notes, index documents, decisions, receipts, and Review payloads are application-encrypted at rest. The organizer and other authorized application services can decrypt the content needed for their scoped operations, and OpenAI receives the disclosed AI-assisted inputs. This is not end-to-end encryption or zero-knowledge storage.

The production configuration accepts exactly the dedicated app-default organizer OpenAI key. BYOK material is not configuration and is resolved only from Vault under a live lease. Generic `OPENAI_API_KEY`, Anthropic variables, arbitrary provider/model/base-URL variables, user sessions, service-role keys, and static AWS credentials remain fatal configuration errors. Model, prompt, schema, and transport-policy changes require a code review plus a pinned evaluation run; queued jobs retain their durable prompt/schema/settings versions and unknown profiles fail before a provider call.

## HTTP contract

- `GET|HEAD /health` returns `{"service":"unfiled-organizer","status":"ok"}`.
- `POST /internal/drain` accepts an empty body (defaults to `schedule`) or exact JSON `{"trigger":"manual|recovery|schedule"}`.
- The request body defaults to 1,024 bytes and is hard-capped at 16,384 bytes. The request deadline defaults to and cannot exceed 49 seconds, leaving a strict margin below the trusted web caller's deadline.
- Success is exact JSON `{claimed,completed,failed,retryScheduled}` with nonnegative safe integers and terminal totals no greater than `claimed`.
- Production accepts the exact web project through Vercel Trusted Sources and separately proves the organizer workload OIDC identity to AWS. `Authorization`, cookies, and protection-bypass credentials are rejected in production.

## Local validation

```sh
pnpm --filter @unfiled/organizer lint
pnpm --filter @unfiled/organizer typecheck
pnpm --filter @unfiled/organizer test:coverage
pnpm test:retrieval-capacity
pnpm --filter @unfiled/organizer build
pnpm --filter @unfiled/organizer test:built-server
```

`pnpm test:retrieval-capacity` is a separately serialized, non-coverage gate. It prepares 1,000 deterministic encrypted 1,536-dimension index fixtures before timing, passes a precomputed query vector directly to the exact private-RAG retriever, and reports cold-cache and warm-cache sample arrays plus p50/p95/max as JSON. Every cold sample must perform exactly 1,000 production-opener decrypts and remain below 2,000 ms p95; every warm sample must rank all 1,000 cached documents with zero decrypts and remain below 250 ms p95. The lane exercises the production envelope opener and ranking implementation with deterministic local key custody; it excludes query-embedding provider time and is not cloud KMS/network evidence.
