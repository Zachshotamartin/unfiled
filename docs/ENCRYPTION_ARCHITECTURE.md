## 1. The honest product promise

Unfiled needs three separate controls:

1. **Transport encryption:** HTTPS/TLS for client-to-API and API-to-provider traffic. Supabase HTTP APIs enforce SSL, and direct Postgres access must additionally enable SSL enforcement with `verify-full` certificate and hostname validation.
2. **Application-level encrypted storage:** this is implemented in code for capture and complete note/library content. A per-object data-encryption key (DEK) uses AES-256-GCM; a key-encryption key (KEK) outside the content store wraps each DEK. The application server may decrypt AI-assisted content briefly in memory. The expand-compatible production schema can still contain its rollback columns until an operator applies the C.5d contract described in §2 and `HUMAN_SETUP.md`; that production operation and its evidence remain launch gates.
3. **End-to-end encryption (E2EE):** only user devices hold a key capable of decryption. Supabase, Vercel, support staff, backups, and AI providers cannot read the content. This is compatible with private manual notes, but it is not compatible with the present server-side AI organizer, server-side plaintext search, or server-side structured mutations.

Therefore the truthful Milestone C.5 promise is **application-encrypted storage for all content, with a separately authorized private-manual key class**. No current mode is E2EE: the owner-authorized application API can decrypt private-manual notes for CRUD, export, and local-in-process lexical search, while the organization worker and AI providers cannot. A future E2EE mode requires a separately accepted design for device enrollment, recovery, synchronization, on-device search, and on-device organization or an explicit disclosure step that is no longer strictly E2EE for the disclosed content.

Do not ship copy such as “only you can read every note” while server-side AI is enabled. The UI must say when content leaves the device, what context accompanies it, and that ordinary API abuse-monitoring retention may apply unless the exact OpenAI project has approved Modified Abuse Monitoring or Zero Data Retention. `store: false` on the Responses request disables Responses application-state storage; it does not apply to the separate Embeddings request and does not by itself establish zero retention.

## 3. Implemented foundation

`@unfiled/content-crypto` provides a small, dependency-free envelope format over the platform Web Crypto implementation:

- AES-256-GCM with a 128-bit authentication tag for both content and DEK wrapping.
- A fresh 256-bit DEK per encrypted object and fresh 96-bit nonces from `crypto.getRandomValues` for every encryption.
- Authenticated associated data binding ciphertext to envelope version, cipher suite, tenant, resource ID, monotonic record version, and content kind. The wrapped DEK is additionally bound to its KEK identifier. Callers must supply the authoritative record version so a ciphertext from another revision is rejected.
- External expected context is mandatory at decryption time, preventing a copied envelope from being accepted as another user, resource, or content type.
- Versioned, strictly parsed, canonical base64url envelopes with bounded input sizes and exact-key validation.
- Non-extractable imported KEKs, generic fail-closed errors, no logger, best-effort zeroing of temporary byte arrays, and no plaintext in errors.
- KEK rotation by rewrapping only the DEK; the content ciphertext remains unchanged.
- Resolver-based decryption that selects the exact authenticated key ID and never silently falls back.

The content-crypto package deliberately does **not** invent key derivation, recovery, KMS access, device enrollment, logging, persistence, nonce-usage accounting, or a migration strategy. C.5a layers a separate, tested `@unfiled/key-management` custody contract and database lifecycle on top instead of coupling those concerns to the envelope primitive. Callers of the byte API own the returned plaintext buffer and must zero it after the shortest practical use; JavaScript strings cannot be reliably erased from memory.

### C.5a managed custody and database capability

`@unfiled/key-management` recognizes exactly four active roots: AI-assisted object-wrap, AI-assisted content-MAC, private-manual object-wrap, and private-manual content-MAC. Production configuration accepts full KMS key ARNs and Vercel OIDC short-lived credentials; static AWS credentials and environment-held production root keys fail closed. The interactive custodian can rewrap roots; the index worker uses a dedicated `index_worker` workload that can generate/unwrap only AI-assisted object-wrap keys, is request-scoped and revocable, and rejects AI content-MAC/private selectors before KMS.

Migration `20260830000015_encrypted_library_expansion.sql` stores only opaque wrapped intermediate-key ciphertext and lifecycle metadata, enforces two-phase activation and irreversible retirement/revocation transitions, and expands each content aggregate with owner/key/context-bound envelope fields. Its `rewrap_user_content_key` RPC is service-only: it locks the key row and compares the expected old root ARN and rewrap count before atomically replacing the ciphertext/root, recording the previous root, incrementing once, and stamping server time. An exact retry replays; stale or mismatched input fails. The isolated worker is explicitly denied this RPC.

The index worker's database authority is `unfiled_index_worker`, an initially `NOLOGIN`, `NOINHERIT`, `NOBYPASSRLS` PostgreSQL role with no table, sequence, private-schema, inherited-role, or public-create privilege. The verifier uses a different exact TLS login, `unfiled_rag_verifier`, with no relation or private-schema capability and exactly two public functions: bounded ciphertext pagination for one building generation and canonical attestation submission. Its separate Vercel/AWS identity can Decrypt only active or retired AI object-wrap roots; it has no data-key generation, content-MAC, private-root, re-encryption, index-write, or activation authority. It strictly opens every projected document before attesting. ### C.5b encrypted aggregate and rollout boundary

`@unfiled/encrypted-aggregate` defines exact typed payloads for note state, revisions, mutations, replay responses, captures, receipts, generated blocks, review/workflow data, taxonomy, and backfill verification. Each sealed object consumes a database-issued owner/class/key/version-bound wrap reservation. Logical writes are prepared before randomized encryption so retries reuse the database-owned note, revision, mutation, job, and capture identities. Request MACs distinguish an exact replay from an idempotency-key conflict; separate verification MACs bind the stored envelope digest and record version without acting as a plaintext content hash. History uses the private key class whenever either side of a privacy transition is private.

Migration `20260830000016_encrypted_aggregate_dual_write.sql` supplies exact-key service RPCs for reservation, prepare/write, encrypted projection reads, verification evidence, deterministic owner-scoped backfill, and rollout transitions. The database owns `expanded → dual_write → encrypted_read`; C.5d deliberately retains ownership of `encrypted_only → contracted`. Legacy writers are serialized against rollout, direct legacy reads are denied from `encrypted_read`, and service reads return only ciphertext plus bounded operational metadata. Counters do not prove completion: the transition rescans exact resources, versions, envelope digests, verification evidence, key state, and in-flight work.

The managed note and capture adapters construct a callback-scoped custodian, aggregate runtime, and strict service-RPC client for each authorized operation. They validate owner/resource/version/kind/key-class bindings, fail closed on unsupported or unavailable operations, and never silently fall back to a plaintext repository. Capture replay first decrypts the stored owner-scoped projection and compares the canonical logical request, so a response-lost retry cannot regenerate a different job, receipt, timestamp, or key reference. The private-manual branch stores an encrypted receipt immediately. C.5d now composes these adapters for Production behind authoritative rollout state; fresh AI-assisted organization remains deliberately gated until Milestone D supplies its evaluated planner/cipher.

### C.5c–E4 isolated organizer boundary

`apps/organizer` is a separately deployable service forming its own Vercel trust domain (`unfiled-organizer`). The organizer's key subset is the AI-assisted object-wrap and content-MAC roots (free beta: the Vercel Sensitive root ring; deferred: the `organization_worker` AWS workload). It can open inputs and seal a complete decision, note mutation, receipt, and Review record under those roots only; it holds no private-manual root and cannot rewrap a root. With complete active-generation coverage, it computes the `unfiled-local-hash-v1` query vector for the capture text in process (no provider request), exact-scans owner-bound encrypted RAG documents in bounded memory, and requests only the exact top-ranked current candidates. Missing, stale, malformed, or incomplete coverage disables RAG-derived auto-apply. ### Milestone E owner-interaction and BYOK boundaries

Owner responses are cursor-bound to 50 rules and 8 MiB per page. Raw request text is limited to 500 UTF-16 code units before NFKC; only Unicode `White_Space` is edge-trimmed and collapsed to ASCII space; lowercase uses locale `und`; trailing Unicode punctuation/whitespace is removed; and the result must contain 1–500 UTF-16 units. This rejects punctuation-only and compatibility-expansion overflow values. U+0085 is treated as whitespace, while U+FEFF is deliberately not. The same canonical payload is encrypted, MAC-bound, learned, and matched so truncation or punctuation boundaries cannot fork identities.

The deterministic rule path remains subordinate to destination and safety policy. The database verifies the snapshot against the exact enabled explicit/accepted rule and immutable revision/priority/destination. ### C.5d encrypted storage contract

C.5d completes the application read/write boundary before making destructive schema change possible. Manual notes, captures, taxonomy, history, undo, search, export, account deletion, and retention use encrypted RPCs and strict ciphertext projections. Search is an authenticated `POST` with private query/paging fields in a JSON body and `Cache-Control: no-store`; query text is never placed in a URL. The isolated organizer is the only configured workflow target, and its request never synchronously chains the independent index worker; no cloud deployment is claimed.

The global contract deliberately separates migration installation from contraction. `private.encrypted_storage_contract_readiness()` binds the exact owner set, rollout/scrub attestations, encrypted and verified object counts, active key slots, RAG safety, and all unfinished claims/reservations into one digest. `private.apply_encrypted_storage_contract(text,text)` is executable only by the real migration owner with `session_user = current_user`; `service_role`, browser roles, and all isolated workloads are revoked. It obtains a fail-fast global advisory lock, then canonical owner locks and table locks, recomputes readiness, and applies all destructive DDL in the caller's transaction. Any stale digest, concurrent application, owner-set change, dependency found by `RESTRICT`, or postcondition failure rolls back the entire operation. A committed contraction has no in-place downgrade; recovery means an explicitly approved restore with separately restored authorized keys.

E1 also includes a private migration-owned repair for legacy organizer receipt timestamps. The upgrade first proves the exact same-owner job/capture/preparation chain, completed transition, consumed reservation, valid envelope context, and matching ciphertext-verification digest. Only then may it replace the relational receipt `created_at` with authoritative capture `client_created_at`; the authenticated ciphertext, receipt revision, and verification record are not rewritten. The repair is unavailable to runtime roles, fails closed on unattested or incomplete state, always restores the ordinary encrypted-write guard, and is idempotent.

## 4. Required key hierarchy

### AI-assisted/server-readable mode

Use one random DEK per content object. Keep the root wrapping keys outside the Postgres database and its backups. The free beta holds them as Vercel **Sensitive** environment variables bound to the exact project and environment, split into four independent families and per-workload subsets ([ADR-0016](./decisions/ADR-0016-free-beta-vercel-sensitive-key-custody-and-local-hash-retrieval.md)); a funded deployment moves them to a managed KMS/HSM. Prefer a per-user intermediate KEK so one compromised key does not expose the entire library; the root wraps that intermediate key, and the intermediate key wraps object DEKs. Cache unwrapped intermediate keys only for a short bounded interval in process memory; never write them to disk, exceptions, traces, analytics, or job payloads. A Node/Web Crypto `CryptoKey` marked non-extractable reduces accidental export but is not equivalent to hardware-backed isolation from a compromised server process.

Track AES-GCM operations per KEK. Random 96-bit nonce uniqueness is a security invariant, not a best-effort optimization. Until an external cryptographic review sets a workload-specific bound, rotate a KEK before `2^24` wraps and immediately after any suspected nonce-generator or key compromise; never retry by reusing a nonce.

The contracted target database stores only the envelope, non-sensitive operational metadata, and the root key identifier. C.5d removes the legacy plaintext contract when its explicit production operation commits; until then, the expand-compatible rollback schema remains a known exposure. Intermediate-key rotation rewraps object DEKs. Root rotation (new root generation plus redeploy in the free beta) re-encrypts the wrapped per-user intermediate key and commits its ciphertext/root metadata through the locked CAS RPC; note ciphertext does not need to change. Retain the previous root as decrypt-only until every reference is verified under the replacement and a restore drill succeeds. Compromise response disables decryption, rotates the affected root/intermediate key as appropriate, rewraps, and audits every use.

### Private-manual application-encrypted mode

Use a separate per-user intermediate-key class and root family for private-manual content (and, in a funded KMS deployment, a separate alias, IAM principal, and audit stream). Object wrapping and content MACs are separate key purposes and are never derived from one another. Key resolution is bound to owner, class, purpose, and key ID. History uses sticky classification: if either side of a privacy transition is private, the revision, mutation, inverse, and replay snapshot remain under the private class.

The organization and index workers must have no decrypt permission for this class, and private-manual notes must produce no organizer projection, embedding, or RAG row. C.5 supplies separately deployable `apps/organizer` and `apps/worker` projects, exact-source caller verification, distinct AI-only root subsets (AWS roles/policies in the deferred custodian), and dedicated non-bypass database capabilities. Neither can share the interactive web/API deployment, root subset, global Supabase credential, or database identity. The owner-authorized interactive API holds all four root families and may decrypt the minimum content needed for CRUD, export, and lexical search in bounded process memory. This is stronger workload separation, not E2EE or zero-knowledge storage. The deployed boundary evidence is recorded in `FINAL_REPORT.md` per `HUMAN_SETUP.md`.

If a future ADR selects E2EE, generate its account root key on a trusted user device and never upload it unwrapped. Passwordless login credentials such as an email address, OTP, JWT, or device ID are not encryption secrets. That future design must choose and test device wrapping, recovery, and key-loss behavior before implementation; it is outside C.5.

## 5. Integration order and concrete touch points

Encryption changes the data model and cannot be safely hidden in one helper call. Implement in this order:

1. **Key custody and policy — code implemented for both custodians; free-beta evidence in `FINAL_REPORT.md`:** deploy distinct web/API, `apps/organizer`, `apps/worker`, `apps/verifier`, and `apps/search` projects and give each only its root subset: web all four families; the organizer the AI object-wrap and content-MAC roots; worker, verifier, and search the AI object-wrap root only. Every isolated project rejects private-manual, AWS, legacy, local, and public-prefixed key variables at startup. The app-level OIDC caller verification, rotation (generation plus redeploy), revocation, availability behavior, subset denial evidence, and a restore check within plan capability must be witnessed. In the deferred AWS custodian the same subsets become IAM/KMS policies with CloudTrail evidence. Fail closed when custody is unavailable; queue captures without plaintext persistence or route them to an explicitly encrypted local outbox.
2. **Schema and aggregate — implemented; production contraction pending:** retain the already-encrypted capture path and add envelope columns for notes, revisions, generated blocks, mutation snapshots, review copies, and every other content-bearing aggregate, plus content-free RAG/job tables. C.5b adds reservation/replay/CAS/read/backfill capabilities and verified owner-scoped rollout through `encrypted_read`; C.5d adds `encrypted_only`, the explicit global contract, and its postconditions. Keep routing/status metadata outside the envelope only when it is truly non-sensitive. Production drops old note columns only through the reviewed digest-bound operation.
3. **API boundary — managed adapters and Production composition implemented:** encrypt immediately after validation and decrypt only after server-derived-user authorization. Never accept a client-supplied tenant ID as authority. Pass the database row owner, resource ID, and authoritative monotonic revision as the expected decryption context. Enforce revision monotonicity outside the envelope so rolling back the row and ciphertext together cannot silently win. Return generic authentication errors. Every operation selects from authoritative rollout state and fails closed rather than downgrading.
4. **Workflow — organizer/index production composition implemented; provider/account evidence pending:** the organizer claims only lease-bound AI-assisted ciphertext, authenticates the encrypted capture, retrieves only lease-derived active-generation RAG pages, revalidates immediately before provider disclosure, authorizes unknown plans before binding database-issued IDs, allows one replan, seals and self-verifies the complete encrypted aggregate, revalidates before publication, and commits the encrypted note/decision/receipt/Review plus content-free index job atomically. The index worker separately claims that index job, decrypts the minimum note projection in a request-scoped KMS session, revalidates immediately before embedding disclosure, treats provider output as untrusted, seals the index document, revalidates again, and publishes ciphertext. Both emit content-free telemetry. Production never falls back to a deterministic Local/Preview planner; activation requires the dedicated provider project, live stochastic report, and canary evidence in `HUMAN_SETUP.md`.
5. **Mobile:** keep capture drafts/outbox in SQLCipher under an independently random database key held in Keychain/Keystore, inaccessible to the widget App Group, and configured with the strongest availability class compatible with background sync. The widget App Group snapshot is content-free: it may carry only schema/version and aggregate queue state, never capture text, note text, titles, destinations, tokens, or receipts.
6. **Web:** encrypt IndexedDB draft/outbox content with a non-extractable Web Crypto key stored as a `CryptoKey`. This protects an offline disk copy but not XSS, a malicious browser extension, or compromised origin JavaScript. Enforce a strict CSP, Trusted Types where practical, dependency integrity, no third-party scripts on authenticated pages, and short-lived plaintext in React state.
7. **Search and Realtime — encrypted lexical and hybrid software paths implemented; final/deployed evidence pending:** C.5d removes plaintext SQL full-text/literal indexes and snippets at contraction. The routing/index pipeline pages encrypted per-user retrieval rows with bounded concurrency and decodes only strict, versioned, bounded float32 embeddings; wrong dimensions, non-finite values, and model mismatch fail closed. [ADR-0013](./decisions/ADR-0013-user-hybrid-search-trust-domain.md) is implemented as a fifth service with the dedicated `unfiled_search_worker` TLS login and exact five-RPC ticket allowlist, a separate OIDC/IAM role that can only decrypt active/registered-retired AI-assisted index object-wrap roots, and one fixed provider credential/model. It receives neither an owner ID nor direct tables, `service_role`, organizer/index/verifier/repair/write authority, content-MAC keys, private-manual roots, BYOK, arbitrary endpoints/models, or cross-request plaintext caches. Web mints a 30-second single-claim database ticket binding its authenticated owner, normalized full-request/filter/cursor digest, active complete generation snapshot, and random claim-secret hash. Search receives only ticket + raw secret + exact body, recomputes the digest, atomically claims, pages/decrypts/ranks bound active/current AI-assisted rows, revalidates, and completes or fails. The provider path runs only for an explicit `ai_assisted` filter; default/mixed/private-manual search and every stale/incomplete generation remain lexical-only. Query/content telemetry is forbidden, cursors bind every filter and generation, and source/backlink work stays in the owner-authorized application. Production remains lexical-only until the final F software and account gates pass. Any future E2EE mode must search locally on devices. Realtime may publish only encrypted envelopes and non-sensitive version/state metadata.
8. **Migration — implemented in code; explicit production operation pending:** drive owners through `expanded → dual_write → encrypted_read → encrypted_only`, then require one fresh exact-readiness digest for the global `contracted` transition. Backfill envelopes in resumable owner-scoped batches, verify decrypt-and-keyed-MAC parity without logging content, stop plaintext writes, and complete the scrub before readiness can become true. Migration installation preserves the rollback window; the explicit apply call atomically removes plaintext indexes/functions/views/columns and closes that window. Record exposed backups until expiry.
9. **Exports/deletion:** exports decrypt only on an authenticated user request, stream directly without temporary files, and never contain keys. Deletion removes live envelopes, wrapped DEKs, search artifacts, device wraps, and provider copies where applicable. With a shared KMS root, old backups can still contain a decryptable wrapped per-user key until the published backup window expires; do not claim immediate cryptographic erasure unless the user has an independently destroyable root and a verified destruction record.

Primary code touch points include the rollout-aware production compositions under `apps/web/src/server/product` and `apps/web/src/server/captures`, the managed encrypted repositories under `apps/web/src/server/encryption`, the E1 owner-interaction coordinators and handlers, the E2 routing-rule reader/coordinator/handlers and client surfaces, the E3 generated-block reader/resolver and web/Swift note/Review surfaces, the E4 AI-settings/provider-key handlers and lease-bound organizer credential path, the F runtime under `apps/search`, web search and note-context compositions, web/native F surfaces, the owner export/deletion and retention coordinators, private search, mobile capture/notes repositories, web IndexedDB capture storage, and migrations 15–27 plus E0–F migrations `20260901000001`–`00007`. Production contraction follows the operator runbook only after the schema, KMS, restore, and backup contracts are reviewed together.

## 7. Sources and rationale

- [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) specifies AES-GCM authenticated encryption. The foundation uses 96-bit random nonces and 128-bit tags and treats nonce uniqueness under a key as mandatory.
- [NIST SP 800-57 Part 1 Rev. 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) covers key lifecycle, protection, rotation, recovery, and compromise handling.
- [OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) recommends authenticated modes such as GCM, independent keys, secure random generation, separation of keys and data, and vault/HSM storage.
- [W3C Web Cryptography API](https://www.w3.org/TR/webcrypto-2/) defines the platform AES-GCM and non-extractable `CryptoKey` operations used by the shared package.
- [Apple: Storing Keys in the Keychain](https://developer.apple.com/documentation/security/storing-keys-in-the-keychain) identifies Keychain as the place for small cryptographic keys.
- [Android Keystore](https://developer.android.com/privacy-and-security/keystore) provides non-exportable and, where available, hardware-backed key use restrictions.
- [Supabase SSL enforcement](https://supabase.com/docs/guides/platform/ssl-enforcement) explains that HTTP APIs enforce SSL but direct Postgres connections require explicit enforcement and should use `verify-full`.
- [Supabase Vault](https://supabase.com/docs/guides/database/vault) keeps a project root key separate from encrypted database values, but its decrypted SQL view means it is not E2EE and is not by itself the proposed content-encryption boundary.
- [OpenAI API data controls](https://developers.openai.com/api/docs/guides/your-data) documents ordinary abuse-monitoring retention and the separately approved Modified Abuse Monitoring and Zero Data Retention controls; `store: false` alone must not be represented as zero retention.
- [OpenAI Responses reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) defines `store` as whether a generated response is stored for later API retrieval.
