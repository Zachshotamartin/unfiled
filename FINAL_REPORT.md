Provider adapters:

- The credential's provider selects the adapter; tests prove an OpenAI key is never sent to Anthropic, a Claude key is never sent to OpenAI, and neither reaches retrieval.

## 3. Free-beta custody and retrieval (ADR-0016)

- Custodian `vercel-sensitive-env-v1`: four independently generated 32-byte AES-256 roots (AI object-wrap, AI content-MAC, private-manual object-wrap, private-manual content-MAC) stored only as Vercel Sensitive Environment Variables, bound to the exact project ID and `production`. Web holds all four; organizer holds the two AI roots; worker, verifier, and search hold AI object-wrap only. Root material never leaves Keychain/Vercel; only root IDs appear in the metadata registry.
- Retrieval embeddings: `unfiled-local-hash-v1`, 512 dimensions, a deterministic feature-hash vector computed in process. It keeps note and query text away from any provider merely for retrieval and needs no provider key, but it is not a semantic embedding and ranks weaker than one. Exact-title, rule, and lexical paths remain the primary destinations.
- AWS KMS/Terraform is preserved and validated (26 tests) but not applied; it is deferred paid hardening.

(4) Every web-to-service call was rejected with 401 because the services capped the OIDC token lifetime at one hour while Vercel issues 12-hour tokens (`fix: accept Vercel's 12-hour OIDC token lifetime in the trusted-source check`). (5) The release probe expected `text/plain` for `/robots.txt` while the deployed route serves `text/plain; charset=utf-8` (`fix: expect the charset the deployed robots route serves in the release probe`). (6) The web passed its OIDC token to the services in an `x-vercel-*` request header, a namespace Vercel reserves and strips at its edge, so every service saw no token and rejected the call as a malformed proof; the header is now `x-unfiled-trusted-oidc-idp-token` (`fix: carry the trusted-source OIDC token in a header Vercel does not strip`). Local suites never traverse that edge, which is why none of (1), (4), or (6) was visible before deployment. (7) The organizer's key-custody readiness self-test unwrapped its throwaway record while it was still `pending`, which the sensitive-environment custodian refuses, so every scheduled drain failed closed at `openSensitiveSession`; the record is now activated in memory first, as the index worker already did (`fix: activate the organizer's throwaway readiness key in memory before unwrapping it`). (8) Every capture whose organizer job had failed returned 503 from the read and list endpoints, so no-key owners (the free beta default) never saw a capture they had just made: the API contract required every terminal capture to carry an organization receipt, but the organizer failure path records only the error code. Found by replaying the production read path locally against a synthetic account with the deployed key environment, after service-role table diffs ruled out storage, keys, and migrations. The contract and the iPhone decoder now accept a failed capture without a receipt, and the web 5xx log carries the cause class and code so the next such failure names itself (`fix: read failed captures that carry no organization receipt`). (9) Retry on a failed Inbox capture only replayed the phone's local outbox, so a capture whose organizer job had failed on the server never retried; the phone now falls through to the server retry (`fix: reach the server when retrying a failed capture`). (10) The phone loaded provider key metadata only when Settings opened, so a fresh launch showed the key card and hid Retry for an owner who already had a key (`fix: load provider key metadata on every refresh`). (11) Every real-key organizer job failed `validation_failed` in about two seconds with no cause recorded. A content-free job-failure log line placed the throw at the provider status policy (OpenAI answered 400); recording the provider's own error identity (its `type`, `code`, `param`, and its message only when it begins with "Invalid schema", which names our keywords and never user content) then quoted the exact defects: the strict Structured Outputs schema carried `minLength` and `maxLength`, which strict mode does not accept, and the operation discriminators and `schemaVersion` carried `const` without a `type` key. Both fixed, with a schema test pinned to OpenAI's documented keyword set (`fix: send OpenAI a strict-mode schema so organizing completes`, `feat: record the provider's own error identity when a job fails`, `fix: give every OpenAI schema node a type key`). The first owner capture then organized end to end on production at 2026-09-03 02:30:16 UTC (`job_01M1JFY4`, `gpt-5.6-terra`, 4.4 s) and the second at 02:31:23 UTC (`job_01M1JFR0`, 4.1 s). Both landed in the Inbox as review items rather than notes: the routing policy's warm-up override sends an account's first five captures to review unless a deterministic rule matches, so an empty library starts by asking. (12) Those review items then reached the phone without their capture: every detail read of a `needs_review` capture returned 503, so the review card showed a generic title and only Dismiss. The web's receipt matcher required the decrypted receipt payload's reason codes to equal the row's, but the commit function projects one content-free review reason onto the row (`ambiguous_intent`, `revision_conflict`, or `explicit_destination`) while the authenticated payload keeps the plan's own reasons; no local test had ever paired the two real shapes. Found by replaying the production read path locally with the aggregate diagnostics on, which named `receipt.mismatch-reasons`. Both matchers now accept exactly that shape through one shared rule with tests (`fix: read needs_review captures whose row carries a projected reason`), and the replay reads both owner captures. (13) Resolving one of those review items with New note then returned 503: a resolution seeds the note from the organizer's plan when one exists, and a plan the organizer deferred to review carries no operations, so the note would have been empty and materialization refused it, which the apply path reported as a generic outage.
